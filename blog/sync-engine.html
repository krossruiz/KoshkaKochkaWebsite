Behind the site

Every folder becomes a repo, automatically

How the system that publishes this project directory to GitHub actually decides what's a project.

This site is generated from one messy folder of ~70 things I've built, tinkered with, or cloned to poke at. Nobody hand-curates a GitHub repo per project here — a sync engine walks the folder, decides what's actually a project, publishes it publicly, and mirrors it into this site. This post is the "how it works" for that engine.

Three kinds of folder

Every top-level folder gets sorted into exactly one of three categories. This distinction is the whole trick — most sync tools only know "publish" or "ignore," which breaks the moment a folder is a container for a project rather than a project itself.

project
Has its own source/build markers — gets its own public repo.
collection
Holds one or more nested projects but isn't one itself — each nested project is published under its own name.
resource
Assets, data, or a clone of someone else's repo — never published.

Worked example: a games/ folder containing one game, flappy-dude/, is a collection — flappy-dude is the project and gets its own repo, while games/ itself is never published. A vidgen/ folder containing a cloned copy of someone else's open-source video model stays a resource even though the clone has plenty of code in it, because the classifier checks who the git remote actually belongs to.

Running it

The engine is a single script, no service required:

python github_sync.py          # classify + publish once
python github_sync.py --watch  # do that forever, checking every 5 minutes

Classifications land in admin.json's classification map. Once a folder is classified — by the engine or by you — that decision is permanent; the engine never silently reclassifies something a human already decided.

Watching it happen

Two small apps sit on top of the same engine for when you don't want to read terminal output: a Windows desktop monitor and a phone app (built with Expo), both showing every folder's category, its VCS, and whether it's synced — tap or double-click a row to move a folder between project, collection, and resource by hand.

pip install -r sync-api/requirements.txt
python sync-api/api_server.py     # small local API the two apps talk to
python desktop-app/monitor.py     # Windows GUI

For the phone app, point API_BASE in expoapps/SyncMonitor/App.js at your machine's LAN IP, then npx expo start from that folder.

Version control beyond Git

The engine also recognizes Mercurial, Subversion, and Perforce workspaces — it reports them in both monitor apps so you can see they exist, but it won't silently convert and publish them. Moving code from one of those into a public Git repo is a one-way, structural decision, and that's a call worth making on purpose rather than automatically.
